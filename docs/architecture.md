# 系统架构

## 1. 设计原则

系统采用“成熟全局规划 + 可替换局部避障”的分层方案。强化学习只解决动态局部避障，不重复研究 SLAM、全局地图构建或视觉识别。

Webots `Supervisor` 只负责回合重置、场景随机化和离线指标记录。策略不能读取障碍物真实坐标、速度或未来轨迹，避免使用仿真器的“上帝信息”。

## 2. 数据流

```text
占据栅格地图 ──▶ A* ──▶ 路点管理器 ──▶ 当前局部目标
                                          │
Webots LiDAR ──▶ 扇区化/归一化 ────────────┤
模拟定位 ──────▶ 相对距离和方位 ────────────┤
当前速度 ──────────────────────────────────┤
                                          ▼
                              可替换局部规划器
                              PPO / DWA / Reactive
                                          │
                                          ▼
                              速度限幅与差速轮换算
                                          │
                                          ▼
                                    Webots 机器人
                                          │
                                          ▼
                                  指标与轨迹记录器
```

## 3. 模块职责

| 模块 | 主要职责 | 可验收产物 |
|---|---|---|
| Webots 场景 | 室内地图、机器人、动态障碍、传感器 | 训练、未见测试和综合演示世界 |
| 场景管理 | 带种子的起终点与障碍随机化、物理状态重置 | 可重放的场景配置 |
| 全局规划 | 栅格膨胀、A*、路径简化、局部路点选择 | 路径规划单元测试 |
| 局部规划 | PPO、DWA、规则法统一输入输出 | 可切换的规划器接口 |
| 控制 | 动作归一化、速度变化限制、轮速换算 | 控制边界测试 |
| 训练 | PPO、课程学习、验证、检查点 | 配置、日志和模型权重 |
| 评测 | 批量运行、统一指标、轨迹与失败案例 | CSV、汇总表和论文图 |
| 应用展示 | 本地网页看板、微信小程序离线回放、本机实时与 CloudBase 真机同步 | 地图、进度、传感器、告警、终态结果和完整巡检报告 |

## 4. 应用展示数据流

```text
Webots 巡检运行
      │
      ├──▶ status.json / events.jsonl / inspection bundle
      │                    │
      │                    ▼
      │          patrol-dashboard/v1 投影
      │                    │
      │        ┌───────────┴───────────┐
      │        ▼                       ▼
      │   本机网页看板          微信开发者工具实时模式
      │
      ├──▶ 已校验成功证据 ──▶ 90 帧离线夹具 ──▶ 小程序演示回放
      └──▶ Mac 只出站 sidecar ──HTTPS/HMAC──▶ CloudBase 只读快照 ──watch──▶ 微信真机
                                             └──▶ 终态安全报告 ──登录鉴权──▶ 历史详情
```

网页、云中转与小程序共享 `patrol-dashboard/v1` 字段语义。新生产者还会携带控制步、动态障碍、避障决策与严格点位采样档案；部署窗口内，三端只对缺少这些新增字段的旧 v1 快照注入明确的“证据不可用”默认值，不放宽原有字段校验。云端入口与小程序数据门使用对称的运行生命周期矩阵，联合约束 `terminal/state/outcome`、结果验证、巡检点计数和进度比例，避免矛盾快照形成终态锁或提前显示成功。普通已验证终态且告警历史完整时，云端从已校验 DTO 生成独立的 `patrol-report/v1` 白名单归档；它不临时透传终态原始负载，并在读取时再次校验运行、结果、地图末点、点位采样和告警来源。小程序数据门还会固定当前 `run_id`、拒绝序号回退或同序号冲突；终态结果保留展示，同时继续等待云端出现下一次合法巡检。App 级共享会话保证页面切换不重启数据源，隐藏页面只缓存最新快照以避免无效重绘。离线夹具由脚本从已校验运行目录生成，不手工编造终态指标。云端链路只传监测数据，不下发运动命令。

## 5. Webots 与 Python 的边界

`controllers/` 中的代码只承担 Webots 设备读写与进程入口。观测处理、奖励、规划、训练和指标均放在 `src/indoor_patrol_rl/` 中，以便不启动 Webots也能进行单元测试。

轻量 `DynamicObstacleAvoidanceEnv` 是接口原型；已实现的 `WebotsPatrolEnv` 复用同一观测和动作语义。二者的物理参数并不等价，所以运动学权重只作为 Webots 策略热启动，最终指标必须在 Webots 中重新测量。

## 6. 保底路线

1. 先完成规则避障与点到点导航；
2. 再完成 DWA，确保系统在 PPO 未收敛时仍可演示；
3. 最后接入 PPO，并通过统一测试场景比较；
4. 如果连续控制训练不稳定，可短期使用离散运动原语诊断，但最终实验仍以连续速度控制为目标。
